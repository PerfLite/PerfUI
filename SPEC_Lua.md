## Цель

Дать моддерам писать **логику интерфейса** на Lua: обработчики кнопок, условия, простые вычисления, таймеры. Внешний вид по-прежнему описывается разметкой (`PerfUI_Markup`). Скрипты не должны требовать ни C++, ни перекомпиляции.

Скрипты **не** предназначены для тяжёлой работы (компас каждый кадр, обход тысяч элементов): это остаётся в C++.

## Расположение и зависимости

- Тот же репозиторий PerfUI. Новая папка `modules/lua/` со своей структурой:
  ```
  modules/lua/
    include/PerfUI/Lua/      публичные заголовки
    src/
    tests/
  third_party/lua/           исходники Lua 5.4 (MIT), собираются как C
  ```
- Отдельные цели `PerfUI_Lua` (CMake и xmake). `PerfUI_Core` и `PerfUI_Markup` **не зависят** от Lua: ни include, ни линковки, ни `#ifdef` в их коде. Подключение идёт только через интерфейсы (см. п. 3).
- Опция сборки `PERFUI_ENABLE_LUA` (по умолчанию ON для `PerfUI.dll`, OFF там, где Lua не нужен). Без неё всё остальное собирается и работает как раньше.
- Использовать **чистый Lua C API** с небольшой собственной обёрткой. Не добавлять sol2 или другие тяжёлые зависимости, если аудит не покажет серьёзной выгоды (тогда обосновать в отчёте и ждать подтверждения).
- Lua компилируется **внутрь `PerfUI.dll`**. Моды Lua не линкуют и `lua_State*` через границу DLL не передают.

## Правила для всех этапов

- C++20. Публичные сигнатуры PerfUI не менять, только добавлять. Новые классы помечать `PERFUI_API`, если они пересекают границу DLL.
- Работать по этапам и **останавливаться после каждого**, ждать моей проверки.
- Тесты на `MockRenderBackend`, регистрировать через `add_test` (CMake) и `add_tests` (xmake). Все существующие тесты проходят. Сборка на MSVC, GCC и Clang.
- Git: коммитить по этапам, `git push` только после моего подтверждения, `git add` по конкретным файлам, без артефактов сборки.
- Скрипты выполняются **только в UI-потоке**. Вызовы из других потоков идут через `RunOnUIThread`. В debug добавить `assert` на проверку потока.

## Этап 1. Ядро: ScriptHost и песочница

### 1.1 Класс

```cpp
class PERFUI_API ScriptHost {
public:
    explicit ScriptHost(std::string name, ScriptLimits limits = {});
    ~ScriptHost();

    bool loadFile(const std::filesystem::path& file);        // выполняет файл в своей среде
    bool loadString(std::string_view code, std::string_view chunkName);
    bool hasFunction(std::string_view name) const;
    bool call(std::string_view name);                        // без аргументов
    bool call(std::string_view name, const ScriptArgs& args);
    void registerModule(std::string name, std::function<void(ModuleBuilder&)> setup);   // для C++ функций мода
    void update(float dt);                                   // таймеры, лимиты
    ScriptStatus status() const;                             // ok / disabled / lastError
    void reset();                                            // пересоздать состояние
};

struct ScriptLimits {
    uint64_t maxInstructionsPerCall{ 1'000'000 };
    float    maxMillisecondsPerCall{ 50.0f };
    size_t   maxMemoryBytes{ 16u * 1024 * 1024 };
    int      maxConsecutiveErrors{ 5 };
};
```

Каждый `ScriptHost` имеет **свой `lua_State`**, чтобы скрипты разных модов не видели друг друга.

### 1.2 Песочница

- Загружать только: `base` (без `dofile`, `loadfile`, `load` с произвольным текстом, `collectgarbage` кроме `"count"`), `table`, `string`, `math`, `utf8`, `coroutine`.
- **Не загружать:** `io`, `os`, `package`, `debug`. Свой безопасный `require(name)` ищет только в папке скриптов того же мода, без выхода за её пределы (`..`, абсолютные пути).
- **Лимит инструкций** через `lua_sethook` (count): при превышении в одном вызове скрипт прерывается ошибкой, в лог идёт сообщение.
- **Лимит времени** на вызов (проверять в том же хуке).
- **Лимит памяти** через собственный аллокатор. Превышение даёт ошибку, а не падение процесса.
- Все вызовы Lua идут через `lua_pcall`. **Ни одно исключение или `longjmp` не должно выйти наружу.**
- Счётчик подряд идущих ошибок. После `maxConsecutiveErrors` скрипт отключается (`status = disabled`), в лог пишется одно понятное сообщение, интерфейс остаётся работать.

### 1.3 Ошибки и логи

- Формат: `[Lua:<mod>] файл:строка: сообщение`.
- Функция `log(...)` в скрипте пишет в лог PerfUI (в игре в SKSE-лог). Уровни: `log.info`, `log.warn`, `log.error`.

### 1.4 Тесты (`modules/lua/tests/ScriptHostTest.cpp`)

1. `io`, `os`, `package`, `debug`, `dofile`, `loadfile` недоступны (`nil`).
2. Бесконечный цикл `while true do end` прерывается лимитом инструкций, хост остаётся рабочим.
3. Выделение гигабайтной строки прерывается лимитом памяти без падения.
4. Ошибка в скрипте, ошибка в вызываемой функции, синтаксическая ошибка: возвращается `false`, процесс жив, в статусе сообщение.
5. После N подряд идущих ошибок скрипт отключается.
6. `require("..\\evil")` и абсолютные пути отвергаются.
7. Два `ScriptHost`: глобальные переменные одного не видны другому.
8. `reset()` очищает состояние.
9. Вызов из чужого потока в debug срабатывает `assert` (если тестируемо).

## Этап 2. API интерфейса и интеграция с разметкой

### 2.1 Что видит скрипт (версия API v1)

Таблица `ui` и значения-ручки (handles):

```lua
local btn = ui.find("SaveButton")      -- ручка или nil
btn:setText("Сохранить")
btn:setVisible(true)
btn:setEnabled(false)
btn:text()                              -- прочитать
ui.toast("Сохранено", "success")        -- success | info | warning | error
ui.timer(2.0, function() ... end)       -- одноразовый, возвращает id
ui.interval(0.5, function() ... end)    -- повторяющийся
ui.cancel(id)
```

Поддержать на ручках те методы, которые безопасно сопоставляются с виджетами (текст `Text`/`Button`, значение `Slider`/`ProgressBar`/`Checkbox`, выбранный индекс `ComboBox`, видимость и доступность любого элемента). Точный список по итогам аудита, каждый метод документировать.

- **Ручки не держат сырых указателей.** Хранить id элемента; перед каждым вызовом проверять, жив ли он. Если элемент уничтожен, метод ничего не делает и пишет предупреждение, а не падает.
- Темы и стили только на чтение (`ui.theme.color("borderFocus")`), без изменения темы целиком.
- Таймеры сбрасываются при `reset()` и при перезагрузке интерфейса.

### 2.2 Привязка к разметке (`PerfUI_Markup`)

- Если `onClick="name"` (и `onChange`, `onFocus` и т.д.) не найден среди C++-колбэков, ищется Lua-функция `name` в скрипте, привязанном к документу. Приоритет C++-колбэков не менять.
- В корне документа: `<UI script="main.lua">`. Путь относительно файла разметки. Вместе с разметкой перезагружается и скрипт (хот-релоад): состояние скрипта сбрасывается, и в лог идёт сообщение.
- Если скрипт упал при загрузке, интерфейс всё равно показывается, а кнопки без обработчика просто ничего не делают (с предупреждением).
- Реализация без зависимости Markup от Lua: интерфейс `ICallbackResolver` в Markup, реализация в `PerfUI_Lua`.

### 2.3 Расширения от C++ (безопасный доступ к игре)

Скрипт **не получает прямого доступа к игре**. Мод сам решает, что открыть:

```cpp
host.registerModule("game", [&](ModuleBuilder& m) {
    m.function("playerHealthPercent", []() -> double { return cachedHealthPct; });
    m.function("playSound", [](std::string id) { ... });
});
```

В Lua это `game.playerHealthPercent()`. Функции вызываются только в UI-потоке и должны читать кеш, а не игровые объекты напрямую.

### 2.4 Тесты

1. `ui.find`, `setText`, `setVisible`, `setEnabled`, значения виджетов: проверка на mock-дереве.
2. Элемент удалён (например, `clearChildren` при хот-релоаде), затем вызов метода ручки: без падения, предупреждение.
3. `onClick="fn"` из XML вызывает Lua-функцию; если есть и C++-колбэк с тем же именем, вызывается C++.
4. Таймеры: срабатывают через `update(dt)`, отменяются, сбрасываются при `reset()`.
5. Хот-релоад разметки и скрипта: новое состояние, старые таймеры отменены.
6. `registerModule("game", ...)`: Lua вызывает C++ функцию, ошибка в C++ функции возвращается как Lua-ошибка, а не падение.
7. Неверные аргументы (`btn:setText(nil)`, `ui.timer("x")`): ошибка скрипта с понятным текстом.
